## Relevance to This Codebase

The platform runs on Windows EC2 instances managed by AWS CodeDeploy with Auto Scaling Groups — no containers, no Kubernetes. Deployments are Ant-built WARs uploaded to S3 and deployed via PowerShell lifecycle scripts. Two independent AWS accounts host US and AU production. The build and deployment cycle exceeds one hour (top-3 operational pain point) and requires manual DevOps involvement for production ASG recovery. Understanding the pipeline is essential for anyone running deployments or modifying build configuration.

## Pipeline Overview

### Build Pipeline (`JenkinsfileBuild.groovy`)

```
Trigger: Manual / PR / scheduled
Stages:
  1. Checkout: abc-j2ee, new-platform-development, aws-code-deploy (three repos)
  2. Config fetch: fetch-and-replace.sh → Config Server → token replace in build properties
  3. Build: ant buildall -DConfig={env}
  4. Package: JSP.war + SessionFixationValve.jar
  5. Upload: artifacts to S3 bucket
```

### Deploy Pipeline (`JenkinsfileDeploy.groovy`)

```
Trigger: Manual (prod) / automatic (non-prod)
Stages:
  1. Create CodeDeploy deployment (referencing S3 artifact)
  2. Production: Blue/Green with ASG swap
     Non-production: In-place with ASG refresh
  3. CodeDeploy lifecycle hooks (via appspec.yml):
     - BeforeInstall: beforeinstall.ps1 — wait for Salt, create temp dir
     - ApplicationStop: applicationstop.ps1 — stop NewPlatform Windows service
     - Extract artifacts to D:\temp\artifacts\
     - ApplicationStart: applicationstart.ps1 — copy WAR to webapps\, start service
  4. Post-deploy: Terraform state update
```

## Configuration Management

All configuration is **baked into the WAR at build time** via token replacement. There is no runtime-dynamic config reload.

| Source | Content | Injection Method |
|--------|---------|-----------------|
| `new-platform/com.abc.npwar/build_1_1.properties` | DB creds, URLs, SMTP, integration endpoints (2752 lines) | Ant token replacement |
| `new-platform/com.abc.npwar/env/build.{env}.properties` | Per-environment overrides | `-DConfig={env}` Ant flag |
| Spring Cloud Config Server | SAML certs, SSO config, BI config, i9 config | `fetch-and-replace.sh` at build time |
| JNDI (`new-platform/ssl/server.xml`) | DataSource connection string | Tomcat runtime |
| `SCHEDULED_TASKS` DB table | Dynamic task schedule | Runtime DB read by jcrontab |

## AI Agent Guidelines for This Area

### Do
- Use `buildall*.bat` scripts for local builds; always pass `-DConfig={env}` explicitly in scripted builds
- Run `fetch-and-replace.sh` before any build that will be deployed — config tokens will not be substituted otherwise
- Reference `new-platform/mappings.json` to understand which properties come from Config Server vs. local files
- When adding a new build-time property, add it to both `build_1_1.properties` (with a `@token@` placeholder) and the Config Server mapping if it is environment-specific

### Do Not
- Modify `codedeploy/scripts/applicationstart.ps1` without testing on a non-production environment first — this is the script that starts Tomcat in production
- Deploy the SCHDL WAR to ASG instances — it must deploy to the dedicated singleton EC2 only
- Hardcode environment-specific values in `build_1_1.properties` — use `@token@` placeholders and override in `env/build.{env}.properties`
- Merge config changes without verifying the Config Server mapping in `mappings.json`

### Always Check
- That `fetch-and-replace.sh` completed successfully before `ant buildall` — a partial fetch produces a broken WAR with unreplaced tokens
- That the correct `-DConfig={env}` flag is passed for the target environment
- The SCHDL EC2 deployment target is separate from the NP ASG in the deployment pipeline
