## Relevance to This Codebase

Background check processing is the core business. The confirmed top operational pain point is order creation failures caused by incorrect package or user configuration — not application bugs but configuration errors that require understanding the order placement flow and the data model to diagnose. Support engineers need to navigate the verification queue system, understand the state machine routing, and know where to look in logs and the database when an order stalls.

## Top Failure Scenarios (Confirmed by Stakeholders)

### Failure 1: Order Creation Fails Due to Wrong Package/User Configuration

**Symptom:** Order cannot be placed; user sees an error on the order form or order is created with no verification components dispatched.

**Root cause areas:**
- `Package` entity missing or misconfigured for the company
- `PackageSearchType` mappings missing for the selected package
- `CompanyConfig` settings missing or incorrect for the client company
- User's role does not include the required `Function` permissions

**Diagnosis steps:**
1. Check `OrderRequest` record in ABCNEW — look at `status` and any error fields
2. Check `Package` table for the company's assigned packages — verify `package_code`, `pkg_name`, and associated `PackageSearchType` entries
3. Check `CompanyConfig` for the client company — verify integration keys (Kenexa/Taleo/eScreen) and queue assignments
4. Check `Abcuser` + `UserRoles` + `RoleFunction` for the submitting user — verify required Function is granted
5. Review Log4j log on the NP EC2 at the time of failure — look for exceptions from `OrderRequestBO` or `Order.java`

**Log location:** `D:\ServerApps\NewPlatform\tomcat\logs\` on the relevant EC2 instance

---

### Failure 2: Request Summary / Result Summary Pages Are Slow

**Symptom:** Pages load slowly or time out; users report performance degradation.

**Root cause areas (most likely):**
- Missing database index on a column used in ORDER BY or WHERE for large result sets
- C3P0 pool near saturation (max 40 connections) causing thread starvation
- Unoptimized HQL query fetching too many entities (N+1 or SELECT *)

**Diagnosis steps:**
1. Check Datadog for EC2 CPU and memory at time of complaint
2. Check C3P0 pool utilization — if pool is near 40, connections are contending
3. Review Log4j for slow query warnings or connection acquisition timeouts
4. Identify the controller handling the slow page (matching `*.do` URL in `JSP-servlet.xml`)
5. Review the HQL queries in the corresponding BO class for missing eager loading or pagination

---

### Failure 3: Deployment Takes >1 Hour / Instance Not in ASG

**Symptom:** Deployment runs much longer than expected; post-deploy health check fails; instance not serving traffic.

**Root cause areas:**
- Salt provisioning step in `beforeinstall.ps1` hanging or timing out
- `applicationstart.ps1` service start retry loop exhausting (Tomcat startup failure)
- ASG instance failed to rejoin after blue/green swap

**Diagnosis steps:**
1. Check Jenkins build log for which CodeDeploy lifecycle step is stalled
2. SSH to EC2 and check Salt service status (if `beforeinstall.ps1` is the issue)
3. Check `D:\ServerApps\NewPlatform\tomcat\logs\catalina.out` for Tomcat startup errors
4. If instance is not in ASG after successful deploy: escalate to DevOps team (manual re-add procedure — Pass 3 Q17)

## Verification Queue State Reference

When diagnosing a stalled verification component, check these DB tables:

| Queue | Table | What It Means |
|-------|-------|--------------|
| Employment (manual) | `employer_code_queue` / `employment_pool` indicator on `VendorRequest` | Awaiting analyst or employer code lookup |
| Employment (international) | `international` queue indicator | International — manual processing |
| Education | `nsc_queue` / `school_id_queue` | National Student Clearinghouse or direct school ID |
| Mail | `mail_queue` | Pending email delivery via `MailQueueManager` |

**VendorRequest status field** is the primary indicator of where a verification component is in its lifecycle. Check `vendor_request` table for the order's components.

## AI Agent Guidelines for This Area

### Do
- Reference `new-platform/com.abc.npwar/config/JSP-servlet.xml` to map a `*.do` URL to its controller, then to its BO — this is the fastest path to the relevant code for any reported issue
- Check `ABCNEW` tables (`order_request`, `vendor_request`, `company_config`, `package`) as the primary diagnostic source for order-related failures
- Document new failure modes in this file as they are discovered

### Do Not
- Assume an order failure is a code bug before ruling out configuration errors — wrong package/user config is the most common cause
- Access production EC2 instances without following the established access procedure (DevOps coordination)

### Always Check
- Whether a reported order failure has a corresponding error in the Log4j log from the NP EC2 at the time of failure
- Whether the company's `CompanyConfig` and `Package` records are correctly configured before escalating to engineering
