## Relevance to This Codebase

The platform carries a 99.9% uptime SLA with a <15-minute RTO and near-zero RPO. Datadog is active at the infrastructure level, but no code-level health check endpoints, application metrics, or structured logging are present. The monolithic architecture (single Tomcat JVM per EC2), sticky-session requirement, and max-40 C3P0 connection pool create scaling constraints. The absence of health check endpoints means the ALB cannot perform HTTP-level liveness checks. Addressing observability gaps is a prerequisite for reliable incident response.

## Scaling Constraints

| Constraint | Detail |
|------------|--------|
| Sticky sessions required | ALB must maintain session affinity — in-memory Tomcat sessions only |
| Not horizontally scalable without sticky sessions | Adding EC2 instances to ASG without stickiness causes auth failures |
| SCHDL must be singleton | jcrontab on multiple instances = duplicate task execution = data corruption |
| C3P0 max 40 connections | All Tomcat threads + SCHDL tasks + MailQueueManager daemon share this pool |

## AI Agent Guidelines for This Area

### Do
- Confirm Datadog log shipping configuration before adding Log4j logging — unnecessary plaintext logs bloat disk and may miss collection
- Add explicit `connectionTimeout` and `socketTimeout` to any new outbound HTTP/SOAP integration calls (Jersey client or Axis)
- Reference `new-platform/com.abc.npwar/config/{env}/log4j.properties` for the current log path when diagnosing issues

### Do Not
- Log full entity objects or request parameters without first confirming PII fields are masked — background check data is highly sensitive
- Add blocking calls that hold a Tomcat thread without a timeout — pool exhaustion cascades to full application unavailability
- Modify C3P0 pool configuration (`hibernate.cfg.xml`) without load-testing first — reducing max connections below current peak usage will cause failures

### Always Check
- Whether a new outbound call (to Kenexa, Taleo, eScreen, or orderproc) has an explicit timeout configured
- That Log4j log level is appropriate for the environment — DEBUG in production fills disk rapidly on a busy system
