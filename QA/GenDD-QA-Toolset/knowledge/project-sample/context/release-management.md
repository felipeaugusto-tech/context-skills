## Rollback Strategy

**Current capability:** CodeDeploy maintains deployment history. Rolling back requires re-triggering a deployment to a previous CodeDeploy revision.

**Limitations:**
- No versioned WAR artifacts in S3 (may overwrite); rollback may require a rebuild
- Database migrations are manual SQL — no automated rollback; forward-only is the current default
- No feature flags for behavior rollback without a full redeploy

**Production rollback steps (current):**
1. Identify last-good CodeDeploy deployment revision
2. Re-trigger deployment to that revision via Jenkins/CodeDeploy console
3. If WAR was overwritten in S3, rebuild from the target Git commit
4. DevOps team re-adds any failed ASG instances manually

**Target RTO:** <15 minutes (confirmed Pass 3 Q16)

## AI Agent Guidelines for This Area

### Do
- Always treat US prod and AU prod as separate independent deploy sequences — they are different AWS accounts
- Coordinate with the DevOps team before any production deployment — manual ASG recovery may be needed
- Verify `fetch-and-replace.sh` completes successfully before `ant buildall` — unresolved tokens produce broken WARs
- Use the `-DConfig={env}` flag explicitly in all scripted builds; never rely on a default

### Do Not
- Assume a WAR built for `prod` can be reused for `au-prod` — they require separate builds with different configs
- Trigger a production blue/green deployment without the DevOps team available
- Modify `appspec.yml` or lifecycle scripts without testing on staging first
- Deploy the SCHDL WAR to ASG instances — it must go to the singleton EC2 only

### Always Check
- That `JenkinsfileDeploy.groovy` is targeting the correct environment and deployment method
- Whether the deployment includes a schema change (manual SQL must be applied separately before or after the WAR)
- That both US prod and AU prod deploys are planned if the change is environment-agnostic
