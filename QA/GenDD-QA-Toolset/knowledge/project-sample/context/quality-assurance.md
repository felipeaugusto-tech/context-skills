Establishing even a thin safety net before any refactoring is the most important QA action.

## Recommended Test Strategy (Phased)

### Phase 1 — Characterization Tests (Do Now, Before Any Refactoring)

Capture existing behavior as tests *before* touching risky code. These are not unit tests in the TDD sense — they describe what the code currently does.

| Target | Approach |
|--------|---------|
| `SecurityFilter.java` | Integration test with mock `HttpServletRequest`/`Response`; test valid SSO token, invalid token, locked account, admin impersonation paths |
| `Order.java` / order placement | Integration test with test DB; verify `Subject`, `Search`, `OrderRequest` records are created atomically |
| `EmploymentStateMachineInitiatorImpl` | Unit test with Mockito; each routing branch (international, no SSN, TWN enabled/disabled) |

### Phase 2 — New Code Tests (Going Forward)

All new code must have unit tests before merging:

| Layer | Test Type | Framework |
|-------|-----------|-----------|
| Controllers | Unit test with `MockMvc` (Spring Test) or Mockito-based mock | JUnit 4 + Mockito |
| Business Objects | Unit test; mock `HibernateManager` | JUnit 4 + Mockito |
| DAO methods | Integration test with test database | JUnit 4 + test DB |
| State machine routing | Unit test; each routing branch | JUnit 4 + Mockito |
| Scheduled tasks | Unit test of BO logic invoked by task | JUnit 4 + Mockito |

### Phase 3 — CI Integration

Once tests exist:
1. Add `ant test` stage to `JenkinsfileBuild.groovy` before the `ant buildall` stage
2. Fail the build if any test fails
3. Add coverage reporting (JaCoCo); set minimum thresholds

## AI Agent Guidelines for This Area

### Do
- Write characterization tests for any component you are about to modify — capture current behavior first
- Use JUnit 4 (`@Test`, `@Before`, `@After`) and Mockito (`mock()`, `when().thenReturn()`, `verify()`) — these are the confirmed available frameworks
- Place test classes in a `src/test/java/` directory mirroring the production source tree
- Mock `HibernateManager` dependencies when testing BO classes in isolation

### Do Not
- Modify `SecurityFilter.java`, `Order.java`, or `EmploymentStateMachineInitiatorImpl.java` without first writing a characterization test that will catch regressions
- Rely on manual testing for any multi-entity write flow — these are the highest data corruption risk

### Always Check
- Whether the component you are generating code for has any existing tests before adding to it
- Whether a new BO method needs a corresponding DAO mock to be testable in isolation
