## Relevance to This Codebase

The AccurateBG New Platform is a classic J2EE layered monolith where all modules share a single Tomcat JVM, a single SQL Server database, and a single Ant build. There are no network boundaries between internal components. Any code change carries the blast radius of the entire application. Understanding architectural constraints is a prerequisite before modifying any code, because layer violations, incorrect transaction scope, or scheduler misconfiguration can corrupt orders or lock users out of the entire system.

## Key Patterns and Conventions

| Pattern | Location | Description |
|---------|----------|-------------|
| Layered request flow | `SecurityFilter` → `DispatcherServlet` → Controller → BO → HibernateManager → DB | All requests traverse this chain; no shortcuts permitted |
| Spring XML-only wiring | `new-platform/com.abc.npwar/config/JSP-servlet.xml` | All controllers, BOs, and DAOs declared as XML beans; no component scanning |
| Singleton scheduler | `new-platform/com.abc.npwar/config/{env}/web-schdl.xml` | SCHDL WAR variant deployed to one dedicated EC2 only — never to ASG instances |
| Build-time config injection | `new-platform/fetch-and-replace.sh` + `build_1_1.properties` | All configuration baked into WAR at build time; no runtime-dynamic config |
| Three-WAR co-deployment | Tomcat `webapps/` | JSP.war + ROOT.war + IntegrationProxy.war share one Tomcat JVM — not microservices |
| HBM entities in external repo | `abc-j2ee` repo — `com/abc/bo/hbm/*.hbm.xml` | Entity schema changes require coordinated commits in `abc-j2ee` AND this repo |

## Architecture Constraints (Non-negotiable)

These constraints are hard facts about the current system. Code changes must respect them:

1. **Sticky sessions are required.** Sessions are in-memory (Tomcat). The ALB must maintain session affinity. Any change that modifies session handling requires ALB validation.
2. **SCHDL WAR = singleton only.** If the SCHDL build variant is ever deployed to more than one EC2 instance, scheduled tasks will execute multiple times causing data corruption.
3. **All config is baked at build time.** There is no runtime config reload. Environment-specific behavior requires a new build with `-DConfig={env}`.
4. **Two data access paths exist.** `HibernateManager` (Hibernate) and `DAConnection` (raw JDBC) both write to ABCNEW. Never mix them in the same transaction flow.
5. **Shared database — no service data boundaries.** There is no schema partitioning. All modules read/write all tables. Treat the entire `ABCNEW` schema as shared state.

## AI Agent Guidelines for This Area

### Do
- Treat `new-platform/com.abc.npwar/config/JSP-servlet.xml` as the single source of truth for bean wiring — always look here to understand what a controller or BO depends on
- Check `new-platform/com.abc.npwar/config/hibernate.cfg.xml` to verify an entity is registered before writing HQL against it
- Check `abc-j2ee` repo for HBM files when making schema-related changes
- Follow the module build order: xsd → hrxml/crossmatch/wsc/wsc.sso → service → newplatform → npwar

### Do Not
- Add new Spring beans via component scanning (`@Component`, `@Service`) — this codebase uses XML-only wiring; annotation-scanned beans will not be found by existing BO/DAO injection
- Deploy SCHDL WAR to ASG instances — it must remain on its dedicated singleton EC2
- Mix `DAConnection` JDBC writes with `HibernateManager` Hibernate writes in the same request thread
- Modify filter ordering in `web-np.xml` without a full auth regression test

### Always Check
- `docs/brownfield/gendd/architecture/overview.md` for system-level context before any structural change
- Whether entity changes require coordinated updates in the `abc-j2ee` repo
- Whether a new endpoint needs to be added to `SecurityFilter`'s internal bypass list (for scheduler tasks)
