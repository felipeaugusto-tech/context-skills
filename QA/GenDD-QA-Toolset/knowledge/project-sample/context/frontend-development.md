## Relevance to This Codebase

The application's user interface is entirely server-rendered JSP with JSTL — there is no client-side JavaScript framework, no component library, and no build tool for frontend assets. The only "frontend" in the modern sense is the marketing site (`ROOT.war`), which is static HTML/JS. UI work is limited to editing JSP pages and their associated JSTL tags. Performance issues on Request Summary and Result Summary pages are a top operational pain point that may have both backend (query) and frontend (DOM size, JavaScript) root causes.

## JSP Development Patterns

### URL Structure

All application URLs end in `.do` and are mapped in `new-platform/com.abc.npwar/config/JSP-servlet.xml`. JSP pages are rendered by controllers as model-and-view responses.

```
Browser → /some-action.do
    → SecurityFilter (auth)
    → DispatcherServlet
    → *Controller.java → ModelAndView
    → JSP view rendered server-side
    → HTML returned to browser
```

### View Location

JSP pages live in `new-platform/com.abc.npwar/web/JSP/`. Each page corresponds to a controller's `ModelAndView` view name. The mapping between a URL and its JSP is:

1. Find the controller URL in `JSP-servlet.xml` (`<value>*.do</value>`)
2. Find the `ModelAndView` returned in the controller
3. The view name maps to a file in `web/JSP/{view-name}.jsp`

### JSTL Usage

JSTL core and formatting tags (`c:`, `fmt:`) are the primary templating mechanism. Data is passed from controllers to JSPs as request attributes set on the `ModelAndView`.

## Performance Considerations

The Request Summary and Result Summary pages are the confirmed slow pages (Pass 3 Q14). Likely root causes span both backend and frontend:

**Backend (higher probability):**
- Missing indexes on ORDER BY / WHERE columns for large result sets
- N+1 HQL queries loading related entities in a loop
- C3P0 pool contention under load

**Frontend (secondary):**
- Large HTML DOM if rendering hundreds of rows without pagination
- Inline JavaScript or blocking script loads
- No server-side caching of rendered fragments

**Recommended approach:** Profile DB query time first (Datadog APM or SQL Server query stats), then browser render time. Fix the larger bottleneck first.

## AI Agent Guidelines for This Area

### Do
- Look up a JSP page by first finding its controller URL in `JSP-servlet.xml`, then the `ModelAndView` view name returned by the controller
- Use `<c:out value="${var}"/>` for rendering any user-supplied or database-sourced text in JSP to prevent XSS
- Add pagination to any JSP that renders a list of records — never render unbounded result sets

### Do Not
- Introduce a JavaScript framework (React/Vue) into JSP pages without a broader architecture decision — it creates an inconsistent hybrid
- Add inline `<script>` blocks with application logic — keep JavaScript minimal and in separate `.js` files in `web/JSP/js/`
- Use `${var}` in JSP for user-supplied content without `<c:out>` escaping

### Always Check
- That the controller sets the required model attributes before the JSP tries to render them — missing attributes produce JSP EL errors
- Whether the performance issue on a slow page is DB-side before adding frontend caching or pagination
