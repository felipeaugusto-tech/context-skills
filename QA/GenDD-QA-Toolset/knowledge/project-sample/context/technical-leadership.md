## Relevance to This Codebase

AccurateBG New Platform carries significant technical debt accumulated across a Java 1.7-source monolith with 200+ vendored JARs, no automated dependency management, no systematic test coverage, and >1-hour build times. Technical leadership context is essential here because modernization decisions — what to fix, what to migrate, and in what sequence — directly affect a revenue-critical SaaS platform with a 99.9% uptime SLA. Every change carries the blast radius of the entire application.

### What's Missing or Weak

| Gap | Impact | Recommendation |
|-----|--------|----------------|
| No dependency management (Maven/Gradle) | HIGH — CVE remediation is impossible without it; JAR upgrades cascade unpredictably | Migrate to Maven or Gradle; start by mirroring current `common-components/lib/` |
| No systematic test coverage | HIGH — Every change is a manual regression burden; `SecurityFilter` (1204 lines) has no tests | Establish characterization tests for `SecurityFilter` and order placement before any refactoring |
| No code quality gates in CI | HIGH — No linting, no coverage thresholds, no static analysis in the build pipeline | Add SonarQube or equivalent once test coverage exists |
| No ADRs or architecture documentation | MEDIUM — Decisions live as tribal knowledge; new engineers can't reason about trade-offs | Retroactively document 3-5 key decisions (Ant over Maven, monolith over services, Tomcat on Windows) |
| Build time >1 hour | MEDIUM — Top-3 operational pain point; slows feedback loop for all developers | Profile Ant build; identify parallelization opportunities |
| No CONTRIBUTING.md or coding standards | MEDIUM — No documented conventions; inconsistency grows over time | Capture existing patterns (BO/DAO naming, Spring XML wiring) as standards |

## AI Agent Guidelines for This Area

### Do
- Reference `docs/brownfield/gendd/` as the authoritative source of system understanding
- Check `docs/brownfield/gendd/risks/risk-hotspots.md` before proposing any change to `SecurityFilter`, order placement, state machine, or Hibernate config
- Respect the module build order defined in `new-platform/build.xml`
- Propose one layer of improvement at a time — this codebase cannot absorb large parallel changes

### Do Not
- Suggest migrating to Maven/Gradle and upgrading libraries simultaneously — sequence migration first, then upgrade
- Propose microservices decomposition without a clear strangler fig plan — the shared database makes clean cuts impossible today
- Add code without checking whether a test can be written for it first

### Always Check
- `docs/brownfield/gendd/risks/risk-hotspots.md` before touching any of the four high-risk areas
- Whether the change requires coordinated edits in `abc-j2ee` (HBM entities) as well as this repo
